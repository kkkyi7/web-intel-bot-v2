Google 开源了一个命令行工具 agents-cli，能让 Claude Code、Codex 等编程助手直接学会在 Google Cloud 上创建、评估和部署 AI Agent，不用开发者手动记一堆云服务命令。
【详细讲给你听】
背景是现在很多开发者用 Claude Code 或 Codex 写代码，但要把 AI Agent 部署到 Google Cloud 上，得学一堆 CLI 命令和云服务配置，门槛很高。Google 这次开源了 agents-cli，本质是一套“技能包”加命令行工具。核心机制是：你装好 agents-cli 后，你的编程助手（比如 Claude Code）就自动学会了 7 个技能，包括工作流管理、ADK 代码编写、项目脚手架搭建、评估方法论、部署到 Cloud Run 或 GKE、发布到 Gemini Enterprise、以及可观测性集成。关键细节有三个：第一，它支持 Antigravity CLI、Claude Code、Codex 等主流编程助手，不锁定生态。第二，评估功能很强，支持 LLM-as-judge 自动打分、多轮对话场景合成、失败模式聚类分析。第三，部署直接对接 Google Cloud 的 Agent Runtime 和 Gemini Enterprise，意味着企业级治理和监控开箱即用。影响是：这大幅降低了在 Google Cloud 上构建生产级 Agent 的门槛，对于做决策智能平台的公司来说，可以把更多精力放在业务逻辑和算法上，不用纠结云基础设施。
【关键术语小词典】
ADK / Agent Development Kit：Google 的 Agent 开发工具包，用来定义工具、编排和状态管理。Gemini Enterprise：Google 的企业级 Agent 平台，提供治理、安全和监控能力。LLM-as-judge：用大模型自动评估另一个模型的输出质量，替代人工打分。Cloud Run / GKE：Google 的容器化部署服务，分别对应无服务器和 Kubernetes。
【对你有啥用】
第一，你正在做决策智能平台，这个工具能让你快速在 Google Cloud 上搭建 Agent 原型并部署给客户演示，省去手动配置云服务的时间。第二，它的评估模块（eval generate / grade / analyze）直接对标你关心的“供应链优化 + AI 应用落地”中的效果验证问题，你可以借鉴它的 LLM-as-judge 和失败模式聚类思路，用在排产算法的效果评估上。第三，下次跟制造业客户（电池、医药）聊时，可以提 Google 已经开源了这套工具链，你的平台能基于它快速帮客户构建供应链决策 Agent，降低客户对“AI 落地太复杂”的顾虑。

【一句话讲清楚它在说啥】
这篇论文提出一种叫 SkillComposer 的新方法，让 AI 智能体不再靠检索或全量暴露来选技能，而是像写程序一样自动生成技能的执行顺序，效果比现有方法好很多。
【详细讲给你听】
背景是现在用 LLM 做复杂任务时，智能体需要调用各种“技能”，比如搭沙箱环境、跑测试、跨文件重构代码。这些技能被封装成模块化包，随着技能库越来越大，怎么选、选几个、按什么顺序用就成了瓶颈。之前的方法要么把所有技能都暴露给智能体让它自己选，要么靠向量检索或 LLM 重排序来召回。但作者发现这些方法忽略了技能组合的结构性——选哪些技能、选几个、按什么顺序，这三个维度是绑在一起的，不能分开处理。核心创新是 SkillComposer，它把技能组合问题形式化为“任务条件化的技能序列预测”，用一个受约束的自回归解码器，在单次解码中同时决定技能子集、数量和顺序，自然捕捉技能间的依赖关系。关键细节：他们在真实人工标注的技能库上构建了训练集，用两个生产级编码智能体在 SkillsBench 上测试。在 GPT-5.2-Codex 和 Gemini-3-Pro-Preview 上，SkillComposer 比无技能基线分别提升了 23.1 和 18.2 个百分点，超越了 top-3 检索方法，并且以更低的提示词成本达到了黄金技能检索的上限。影响是：这改变了我们让智能体使用工具的方式，从“检索+选择”转向“生成式规划”，对工业场景中需要多步骤协作的任务尤其有价值。
【关键术语小词典】
- SkillComposer / 技能合成器：论文提出的方法，自动为任务生成技能执行序列
- 结构化技能组合 / Structured Skill Composition：同时决定技能子集、数量和顺序的组合问题
- 自回归解码器 / Autoregressive Decoder：一种逐步生成序列的神经网络结构，每次预测下一个元素
【对你有啥用】
第一，你做的决策智能平台本质也是帮制造业客户做排程和优化，这和智能体选技能的逻辑高度相似。你可以思考：能不能把排产算法中的工序选择、资源分配、顺序优化也建模成这种“结构化组合”问题，用类似方法提升效率。第二，下次跟电池或钢铁客户聊排程时，可以提这个思路：传统排程是检索历史方案或全量枚举，但更聪明的方式是像 SkillComposer 一样，根据当前订单和产线状态，自动生成最优的工序序列。第三，你关注 AI Agent 应用，这篇论文直接告诉你：未来智能体调用工具的方式会从“检索式”转向“生成式”，这对你设计产品中智能体的行为逻辑有启发，比如在供应链优化中，可以让智能体自动组合“需求预测-库存检查-采购建议”等技能。

【背景知识】
这篇论文解决的是 LLM Agent 技能调用的结构化组合问题——传统做法要么把所有技能一股脑塞给模型让它自己选（浪费 token 且容易出错），要么靠向量检索召回（忽略技能之间的依赖关系）。SkillComposer 的核心是把技能选择、数量、顺序三个维度打包成一个序列预测任务，用自回归解码器一次性生成，类似把“选工具”变成了“写脚本”。不过要注意，这个方法依赖高质量的人工标注技能库来训练，如果技能库本身质量差或者任务边界模糊，效果会打折扣。

When LLMs Read Tables Carelessly: Measuring and Reducing Data Referencing Errors

【一句话讲清楚它在说啥】
这篇论文发现大模型在处理表格数据时，经常引用错数字或漏掉关键数据，然后他们训练了一个轻量级“纠错模型”来检测这些错误，能把最终答案准确率提升最多 12%。
【详细讲给你听】
背景是现在很多 AI 应用，比如供应链排程、财务分析、客户报表解读，都需要大模型去读表格。之前大家主要看模型最后答得对不对，但很少关注它在推理过程中有没有“看错行”或“抄错数”。这篇论文是第一个系统性地研究这种“数据引用错误”的工作。核心发现是：所有测试的模型，从 1.7B 到 20B 参数，都会犯这类错误。关键细节有三点：第一，错误普遍存在，不是大模型就不犯错；第二，他们设计了一个“批评者”机制，让模型自己检查自己引用的数据对不对，通过过滤和拒绝采样，最终答案准确率提升了最多 12%；第三，他们训练了一个只有 4B 参数的轻量级批评模型，检测这种错误的 F1 分数达到 78.2%，而且能帮更大的模型做推理纠错。说白了，这就像给读表的 AI 配了一个“校对员”，专门盯着它有没有抄错数。
【关键术语小词典】
- DRE / Data Referencing Error：数据引用错误，指模型在推理时错误引用或遗漏表格中的具体数值。
- Critic Model / 批评模型：一个专门用来检查另一个模型输出是否正确的辅助模型。
- Rejection Sampling / 拒绝采样：一种方法，通过多次采样并丢弃不满足条件的输出，来提升最终结果质量。
【对你有啥用】
第一，你做的决策智能平台核心就是处理表格数据，比如供应链的 BOM 表、排程的产能表、电池的工艺参数表。这个研究直接告诉你，你用的底层模型大概率会在这些表上犯低级错误，而且你之前可能没意识到。第二，你可以把这个“批评模型”的思路搬到产品里：在用户看到 AI 给出的排产建议或供应链优化结果之前，加一层自动校验，专门检查 AI 引用的数据是否和原始表格一致。这能极大提升客户（尤其是制造业客户）对 AI 输出的信任度。第三，下次和客户沟通时，你可以主动提“我们做了数据引用错误检测”，这比只说“我们用了大模型”更有说服力，因为客户最怕的就是 AI 瞎编数据。
