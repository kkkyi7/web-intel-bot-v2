AirLLM：单张4GB显卡跑70B大模型
lyogavin/airllm
GitHub Trending
⌄
https://github.com/lyogavin/airllm

【一句话讲清楚它在说啥】
AirLLM这个开源工具通过分层流式加载技术，让超大模型（70B甚至671B）能在极低显存（4GB到12GB）的普通显卡上运行，不用量化裁剪，直接推理。
【详细讲给你听】
背景是，大模型越来越大，动辄几百B参数，一般开发者手里只有消费级显卡，显存根本装不下。以前要么租云服务器，要么用量化压缩，但都会损失精度或增加复杂度。AirLLM的思路很直接，不一次加载整个模型，而是按层加载，算完一层就释放，再加载下一层，这样显存占用就只跟单层大小有关，跟模型总大小无关。核心是它把模型切成很多层，推理时逐层在GPU和内存之间搬运，速度慢一点但能跑起来。关键细节有三个，一是70B模型在4GB显卡上能跑，二是405B的Llama 3.1在8GB上能跑，三是671B的DeepSeek-V3在12GB上能跑，最新的Kimi K3（2.8T参数）在4GB内也能跑，因为稀疏MoE模型每次只加载一个专家，而不是整层。影响是，这大大降低了个人开发者玩超大模型的门槛，不用买昂贵硬件，也不用依赖云服务，本地就能实验和部署。对做产品的人来说，这意味着推理成本可以大幅下降，边缘设备或小规模部署成为可能。
【关键术语小词典】
MoE（混合专家模型）：把模型分成多个专家模块，每次只激活少数几个，省算力。
显存（VRAM）：显卡上的专用内存，决定能装多大模型。
量化（Quantization）：压缩模型精度来减少内存占用，AirLLM不需要这个。
分层加载（Layer-wise Streaming）：按层依次加载模型到显存，算完就释放。
【对你有啥用】
第一，你做决策智能平台，如果客户有私有化部署需求，尤其制造业客户IT资源有限，AirLLM这种低显存推理方案可以直接写进方案书，跟客户说不用买高端服务器，普通工作站就能跑大模型，这能降低客户决策门槛。第二，这个思路跟排产算法里的分步求解很像，都是把大问题拆成小块逐个处理，下次跟客户聊优化方案时，可以用这个类比解释为什么复杂模型也能在有限算力下落地。第三，你关注AI Agent和工具产品，AirLLM这类开源项目是典型的开发者工具，值得研究它的社区运营和文档结构，看它怎么吸引开发者，这对你做平台产品的开发者生态有参考价值。

【背景知识】
AirLLM 解决的是大模型推理的显存瓶颈问题。传统推理需要把整个模型权重常驻显存，而它通过分层流式加载，把计算拆成逐层处理，显存占用从模型总大小降到单层大小。代价是推理速度明显变慢，因为每层都要在磁盘、内存和显存之间搬运数据，所以它更适合离线批处理或对延迟不敏感的场景，不适合实时交互。另外，它虽然支持 4bit/8bit 量化，但核心卖点是不量化也能跑，这跟主流量化方案（如 GPTQ、AWQ）形成互补而非替代。

【一句话讲清楚它在说啥】
这篇论文提出一个叫 STAIR 的框架，把 AI 修代码的历史过程整理成多层级的可复用计划，下次遇到类似 bug 直接套用，不用从零开始，在 SWE-bench 测试上把修复成功率提到了 81.2%。
【详细讲给你听】
背景是这样的：现在用大模型驱动的编码智能体确实能修复杂的仓库级 bug，但有个大问题，每次修完就完了，经验全丢，下次遇到类似问题还得从头推理一遍，既慢又容易出错。这就像老师傅修机器，修完一台就把手艺忘光，下一台重新摸索。

STAIR 的核心思路是把每次修复过程变成一棵多层级树，从最细的"诊断动作"到最粗的"修复策略"都存下来。新问题来了以后，它从不同层级挑出相关的计划节点，拼成一个针对当前问题的可执行方案，塞进提示词里给智能体用。相当于给 AI 配了个"维修手册"，而不是每次裸奔。

关键数据有三个：一是 STAIR 配合 Lingxi 智能体，在 SWE-bench Verified 上达到 81.2% 的通过率，用 GPT-5 也有 79.2%；二是生成的计划能跨智能体迁移，把另一个结构完全不同的 mini-SWE-agent v2 从 75.8% 拉到 81.0%，不用改一行代码；三是消融实验证明，混合多个抽象层级比只用单一层级效果好，原始未抽象轨迹的迁移效果明显更差。

对产品经理来说，这个思路的本质是"经验的结构化沉淀与复用"，跟知识管理、最佳实践库是同一个逻辑，但做到了自动化、可检索、可适配。
【关键术语小词典】
SWE-bench Verified：一个评估 AI 修真实 GitHub 代码问题的标准测试集，行业公认的标杆。
Pass@1：AI 第一次尝试就成功修复问题的比例，越高代表能力越强。
轨迹抽象：把完整过程压缩成不同粒度的摘要，保留关键步骤和策略，去掉无关细节。
Lingxi：一个编码智能体系统，类似 Cursor 里的自动修 bug 代理。
【对你有啥用】
第一，这个"多层级经验复用"的思路可以直接搬到你的决策智能平台里。客户工厂里每次排产优化、每次异常处理都是轨迹，如果能把历史决策过程抽象成可复用模板，下次遇到类似订单结构或设备故障，直接推荐方案，这比每次重新跑算法快得多，跟客户聊"经验沉淀"比聊"算法精度"更容易打动制造业客户。

第二，它验证了一个产品判断：在 AI 应用层，数据飞轮的关键不是存原始日志，而是把日志加工成结构化、多粒度的"经验包"。你给客户做供应链优化时，别只交付结果，要把"为什么这么排"的推理过程也沉淀下来，这才是可迁移的产品壁垒。

第三，跨智能体迁移这个结论对你选型有参考价值。如果一套计划模板能适配不同底层模型，那你在做平台时就不用绑定某一家大模型，降低供应商锁定风险，这个卖点可以写进方案里。

编码智能体（coding agent）是当前 AI 编程领域的热点，它们能自主定位并修复代码仓库中的 bug。但主流做法是每次任务都从零开始推理，历史修复经验无法沉淀复用，导致效率低下且难以应对复杂问题。这篇论文提出的 STAIR 框架，本质上是把修复过程抽象成多层级轨迹（从细粒度动作到粗粒度策略），并实现跨智能体的迁移复用。值得注意的是，这种思路并非全新概念，类似经验复用或案例推理（CBR）在传统软件工程中早有研究，但 STAIR 将其与现代 LLM 智能体结合，并验证了在 SWE-bench Verified 上的显著提升。不过，其效果高度依赖轨迹质量，且对全新类型 bug 的泛化能力可能有限。

Google 给 Gemini API 的托管代理加了一堆新能力，包括更快的 3.6 Flash 模型和钩子机制，让开发者能更轻松地构建可靠的生产级 AI 代理，不用自己管底层基础设施。
【详细讲给你听】
背景是现在做 AI 代理（Agent）最大的痛点不是模型不够聪明，而是工程化太麻烦：要处理上下文、要管理工具调用、要处理错误重试，这些活儿如果全靠自己写代码，一个代理从原型到上线得花好几周。Google 之前推出了托管代理（Managed Agents），相当于把代理运行时的脏活累活全包了，开发者只需要定义逻辑和工具。这次更新是把这个托管服务往前推了一大步。核心是两件事：第一，接入了 3.6 Flash 模型，这个模型主打低延迟和高吞吐，特别适合代理这种需要多轮交互的场景，比之前的版本在速度和成本上都有优化。第二，引入了钩子（hooks）机制，这玩意儿说白了就是允许开发者在代理执行的关键节点插入自定义代码，比如在调用外部工具之前做权限校验，或者在模型返回结果之后做格式清洗。这个机制让托管代理从"黑盒"变成了"可干预的灰盒"，大大提升了可控性。另外还提到了一些配套更新，比如更好的上下文管理工具和调试面板。整体来看，Google 在赌一个方向：未来大部分企业级 AI 应用不会是单体模型调用，而是多个代理协作的复杂系统，而托管代理就是降低这个系统搭建门槛的钥匙。
【关键术语小词典】
Managed Agents / 托管代理：由云平台托管运行环境的 AI 代理服务，开发者不用管服务器和运维。
Hooks / 钩子：在特定事件发生时自动触发的自定义函数，用于在代理执行流程中插入逻辑。
Gemini 3.6 Flash：Google 的轻量级多模态模型，主打低延迟和成本效率，适合高频调用场景。
【对你有啥用】
第一，你做的决策智能平台如果涉及多步骤流程（比如供应链异常检测后自动触发补货建议），这个托管代理的思路可以直接借鉴：把复杂决策拆成多个子代理，每个负责一个环节，用钩子做数据校验和结果格式化，能大幅减少你团队处理工程边角料的时间。第二，下次跟客户聊排程算法优化时，可以提"我们正在评估用托管代理来封装排程逻辑，让业务人员能通过自然语言触发重排，同时保留钩子接口做权限控制"，这比单纯讲算法精度更能打动制造业客户。第三，你关注 AI Agent 学习路径，这篇是很好的"平台化"案例，值得拆解 Google 是怎么把代理的运行时标准化、产品化的，这对你理解 Agent 从 demo 到生产环境的差距很有帮助。

核心：作者们不追求“万能最优”，而是提出一个框架，让你根据分析目标，在某一类试验里系统选出最合适的估计器。方法是把样本拆成两部分，一部分用来估计不同估计器的误差分布，另一部分做验证，保证比较结果有统计保证。他们用亚马逊供应链优化试验和“强化民主挑战”数据集（25个干预措施）做测试，发现目标不同，最优选择完全不同。

机制与影响：这本质上是个“元选择”问题，不直接改进某个估计器，而是帮你选对工具。对供应链场景来说，意味着你在做A/B测试或试点评估时，不用再默认用某个标准方法，而是可以按业务目标动态选。商业价值在于，减少试错成本，提高决策质量，尤其在排产、库存优化这类高不确定性场景里，选对估计器可能直接影响ROI。
