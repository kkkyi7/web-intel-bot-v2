【一句话讲清楚它在说啥】
一个叫 Multica 的开源项目，把 Andrej Karpathy 吐槽 LLM 写代码的毛病总结成四条原则，放进一个 CLAUDE.md 文件里，用来调教 Claude Code 的行为，让它少犯错、不瞎改、不写废话代码。
【详细讲给你听】
背景是 Karpathy 之前发帖吐槽 LLM 写代码的几个通病：模型会替你瞎做假设然后直接跑偏，不会主动澄清困惑，喜欢把代码搞复杂，动不动写一千行其实一百行就能搞定，还会顺手改掉它看不懂的注释和代码。这个项目就是针对这些痛点，把解决方案浓缩成一个 CLAUDE.md 文件，直接喂给 Claude Code。核心是四条原则：第一，先思考再编码，要求模型显式列出假设、主动提出替代方案、在不确定时追问而不是瞎猜。第二，简洁优先，禁止任何超出需求的抽象、配置和错误处理，如果两百行能缩成五十行就重写。第三，外科手术式修改，只动你被要求改的地方，不改旁边的代码、注释和格式，发现死代码只能提不能删。第四，目标驱动执行，把“加个验证”变成“先写测试让测试通过”，每个步骤都要有明确的验证标准。这个文件已经在 GitHub 上开源，可以直接集成到 Claude Code 的插件里。
【关键术语小词典】
- CLAUDE.md：Claude Code 的项目配置文件，用来定义编码风格和行为规则。
- Multica：一个开源平台，用于运行和管理编码代理，支持可复用的技能模块。
- Andrej Karpathy：前特斯拉 AI 总监、OpenAI 研究员，以对 LLM 的犀利观察著称。
【对你有啥用】
第一，这个思路可以直接用到你做的决策智能平台里。你们的产品在给制造业客户做排程优化时，AI 模型同样会犯“瞎假设、不澄清、过度复杂化”的毛病。你可以把类似的原则写进产品文档或 prompt 模板里，比如要求模型在输出排程方案前先列出假设条件、主动提示冲突点。第二，作为 PM，下次跟客户聊 AI 落地时，可以拿这个例子说明“不是 AI 不行，是没给它好的行为约束”。客户经常抱怨 AI 不靠谱，你可以说“我们正在用类似 Karpathy 的方法给模型加行为准则，让它先思考再输出”。第三，你自己在学 AI Agent 和 LLM 应用，可以直接把这个 CLAUDE.md 文件下载下来，在 Cursor 或 Claude Code 里试试效果，对比加与不加的差异，这对理解 prompt 工程和 Agent 行为控制非常有帮助。

Evaluating Commercial AI Chatbots as News Intermediaries

【一句话讲清楚它在说啥】
这篇论文系统测试了GPT-5、Claude 4.5等六个主流AI聊天机器人，用2100个基于BBC新闻的事实问题评估它们的信息准确性，发现模型在英语地区表现好，但在印地语等非英语区域准确率暴跌，且大部分错误源于检索失败而非推理能力不足。
【详细讲给你听】
背景是AI聊天机器人正成为越来越多人获取新闻的入口，但此前没人系统测过这些带搜索功能的模型在不同语言和地区的信息准确性。核心实验是：研究团队在2026年2月9日至22日这14天内，从BBC六个区域服务（美加、阿拉伯、非洲、印地语、俄语、土耳其语）的当天新闻中提取了2100个事实性问题，让Gemini 3 Flash/Pro、Grok 4、Claude 4.5 Sonnet、GPT-5和GPT-4o mini这六个模型作答。关键发现有三：第一，所有模型在印地语上准确率最低（79%），远低于其他语言的89-91%，且模型回答印地语问题时引用英文维基百科的次数比引用任何印地语媒体都多，说明存在明显的英语检索偏见。第二，超过70%的错误是检索失败导致的——模型如果能找到正确来源，基本能提取出正确答案，但问题在于它第一步就找错了地方。第三，当问题包含微妙的错误前提时，模型准确率从88-96%暴跌到19-70%，最脆弱的模型有64%的概率会接受捏造的事实。还有一个反直觉的发现：最好的错误前提检测器在对抗准确率（即拒绝回答率）上只排第二，而一个更弱的检测器排第一，说明前提检测和答案恢复是部分独立的能力。整体来看，高准确率可能掩盖了系统性的地区不平等、对检索基础设施的近乎完全依赖，以及面对真实用户不完美提问时的脆弱性。

【对你有啥用】
第一，这个发现直接冲击你作为决策智能平台PM的核心工作：如果你在帮制造业客户做供应链优化或排程算法，模型的检索偏见问题同样存在。比如用AI处理多语言BOM表或供应商数据时，英语语料占优的模型可能忽略非英语地区的关键约束条件，导致排产方案在本地失效。第二，对产品沟通的启发：下次跟电池或医药客户聊AI落地时，可以主动提这个研究，说明“高准确率不等于高可靠性”，建议客户在非英语场景或数据稀疏的细分领域做额外的检索验证层，这能体现你的专业深度。第三，对学习路径的指导：论文揭示的“检索失败是主要瓶颈”说明，你在研究AI Agent和LLM应用时，应该把更多精力放在理解检索增强生成（RAG）的工程细节上，而不是只关注模型推理能力的提升。这对你今年“深化工业软件+AI产品理解”的目标直接相关。

【一句话讲清楚它在说啥】
这篇论文发布了一个叫GS-QA的地理空间问答基准，包含2800个问题，测试大模型能不能回答“从A到B多远”这类需要地图和百科知识的问题。结果发现现有模型在复杂问题上表现很差。
【详细讲给你听】
背景是现在大模型在问答上进步很快，但地理空间问答一直没人好好测。以前的数据集要么问题太少，要么只测简单方向，比如“北京在哪”，不会测“上海和杭州之间有多少个城市”这种需要多源信息的问题。核心是作者们基于OpenStreetMap和维基百科数据，造了2800个问答对，覆盖28种模板，包括实体名称、位置、距离、方向、计数和聚合面积/长度。关键细节有两个：一是有些问题需要同时用地图数据和百科事实数据才能回答，比如“离北京最近的省会城市人口是多少”；二是他们用了9种大模型方案测试，包括GPT-4o、Claude Sonnet 4.6和Ministral-3，结合了直接提示、检索增强生成和文本转SQL三种方法。结果发现，简单问题模型还行，但一旦涉及复杂空间关系、数值输出或多源推理，准确率就大幅下降。这意味着地理空间问答对工业软件来说还是个硬骨头。
【关键术语小词典】
GS-QA：地理空间问答基准，专门测试模型处理地图和位置相关问题的能力。OpenStreetMap：开源地图数据，类似谷歌地图但由用户贡献。Spatial Predicate：空间谓词，比如“在...里面”、“朝向”、“距离”这类描述位置关系的词。Text-to-SQL：把自然语言问题转成数据库查询语句的技术。
【对你有啥用】
第一，你在做供应链优化和排程算法，客户经常问“原材料从哪个仓库调最近”或“工厂A到港口B的运输时间”，这类问题本质就是地理空间问答。GS-QA的失败案例直接告诉你，现有大模型在处理这类问题时有多不靠谱，所以别指望纯AI能搞定，得结合传统空间数据库或排程引擎。第二，你的决策智能平台如果要做“供应链可视化”或“物流路径推荐”功能，可以借鉴GS-QA的多源推理思路，把地图数据和业务数据（如订单、库存）打通，而不是只靠大模型瞎猜。第三，这篇论文的评估方法很实用，他们用了距离误差和角度误差来量化模型回答的准确度，你以后跟客户汇报AI方案效果时，可以引用类似指标，显得专业。

Python 的包管理工具 Pip 出了新版本，加了两个关键功能：一个是“依赖冷却”，防止你刚装完包就立马被恶意更新坑到；另一个是实验性的锁定文件，能固定住所有依赖版本，避免供应链攻击。
【详细讲给你听】
背景是，现在软件供应链攻击越来越猖獗，攻击者会通过劫持一个你常用的开源包，然后推送恶意更新，你的 CI/CD 流水线一跑，就把病毒拉进来了。之前 Pip 在这方面防御很弱，基本是“你说更新我就更新”。这次 Pip 26.1 主要做了两件事。第一是“依赖冷却机制”：当你安装一个包后，Pip 会强制等待一段时间（比如几分钟或几小时）才允许你再次安装它的新版本，这能有效阻断“刚发布恶意版本就被自动化工具拉取”的攻击。第二是实验性的锁定文件功能，类似 Node.js 的 package-lock.json，它能记录下所有依赖的精确哈希值，下次安装时强制校验，确保你拿到的包和开发时一模一样。这两个功能合起来，相当于给 Python 项目的依赖管理上了双保险。对于做工业软件的你来说，客户的生产环境往往非常敏感，这种能精确控制依赖版本和安装时机的机制，直接关系到你产品的稳定性和安全性。
【关键术语小词典】
- 依赖冷却机制：安装包后强制等待一段时间才能更新，防止恶意版本被立即拉取。
- 锁定文件：记录所有依赖的精确版本和哈希值，确保每次安装的包完全一致。
- 供应链攻击：攻击者通过污染上游开源软件或依赖，来感染下游使用者的系统。
【对你有啥用】
1. 跟客户聊安全合规时，可以直接提“我们的 AI 平台底层依赖管理已经引入了类似 Pip 26.1 的依赖冷却和锁定机制，能有效防止供应链攻击”。这在电池、医药等受监管行业是加分项。
2. 你在做排程算法或决策智能平台时，肯定依赖大量 Python 库（如 pandas、numpy、scipy）。建议你立刻在自己的开发环境和 CI/CD 流水线里启用 Pip 26.1 的锁定文件功能，避免某天某个底层库被投毒导致整个平台崩溃。
3. 这个思路可以迁移到你自己的产品设计里。比如，你的平台是否也有“依赖”或“插件”机制？是否应该引入类似的“冷却期”或“版本锁定”来防止用户误操作或恶意更新？这是产品安全设计的一个好案例。
