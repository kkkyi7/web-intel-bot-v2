【详细讲给你听】
背景是现在AI编码代理虽然能写代码，但缺乏工程化思维，容易写出“能用但不可维护”的代码。这个项目由Google Chrome团队的技术负责人Addy Osmani发起，核心是把资深工程师的完整开发流程——从需求定义、规划、构建、测试、审查到发布——编码成AI代理能执行的技能包。关键细节：它提供了7个斜杠命令（/spec、/plan、/build、/test、/review、/ship），每个命令对应一个开发阶段并自动激活相关技能。比如你输入/build，它会自动生成计划并逐个任务实现，每个任务都是测试驱动的，遇到失败会暂停。它还支持自动技能检测，比如设计API时自动触发api-and-interface-design技能。影响是让AI代理从“写代码的工具”变成“遵循工程规范的开发者”，特别适合需要代码质量和流程一致性的团队。项目已支持Claude Code、Cursor、Gemini CLI、GitHub Copilot等8种主流工具。
【关键术语小词典】
- Agent Skills / 代理技能：把资深工程师的开发流程和最佳实践打包成AI能执行的指令集

HyperTool：超越逐步工具调用的智能体新范式
HyperTool: Beyond Step-Wise Tool Calls for Tool-Augmented Agents
arXiv · Yaxin Du, Yifan Zhou, Yujie Ge, Jiajun Wang, Xianghe Pang, Shuo Tang, Tuney Zheng, Bryan Dai, Jian Yang, Siheng Chen · 2 天前

【一句话讲清楚它在说啥】
这篇论文提出HyperTool，让AI智能体不再一步步调用工具，而是把多个工具操作打包成一个代码块一次性执行，大幅提升多步工具使用的准确率。
【详细讲给你听】
背景是现在的大模型做工具调用时，每用一个工具都要在推理轨迹里暴露一次调用、一次观察、一次值传递，这就像让一个厨师每切一次菜都要停下来写个报告，效率极低。核心问题是执行粒度不匹配：那些确定性的工具流程被拆成了无数个模型可见的决策步骤，既浪费上下文，又让模型去管理底层数据流。HyperTool的解决方案很聪明，它设计了一个统一的可执行工具接口，模型只需要写一个代码块，里面可以调用多个现有工具、操作返回值、传递中间结果，整个确定性子流程被压缩成一次外部调用。关键数据：在MCP-Universe测试集上，Qwen3-32B的准确率从15.69%提升到35.29%，Qwen3-8B从9.93%提升到33.33%，甚至超过了GPT-OSS和Kimi-k2.5。这相当于给AI配了个“自动化流水线”，而不是让它每次拧螺丝都要请示。
【关键术语小词典】
- MCP / 模型上下文协议：一种标准化接口，让AI模型能统一调用外部工具和数据源
- Tool-Augmented Agents / 工具增强型智能体：能调用外部工具（如搜索、计算）来完成任务的大模型系统
- Execution-Granularity Mismatch / 执行粒度不匹配：模型处理工具调用的步骤粒度与实际工具操作的粒度不一致，导致效率低下
【对你有啥用】
第一，这个思路直接可以迁移到供应链排程场景。客户工厂里那些确定性的排产规则（比如换产时间计算、物料约束检查）完全可以打包成HyperTool式的代码块，让AI一次执行，而不是一步步问用户。第二，你在做产品设计时，可以跟客户讲“我们不是让AI一步步问你怎么操作，而是把整个工序包成一个智能体”，这比解释技术细节好卖得多。第三，这个论文的方法论对你在AI Agent方向的学习路径有启发：别只关注单步调用，要思考如何把确定性流程抽象成“黑盒”，这对产品架构设计是核心能力。

【背景知识】
传统上，AI智能体调用工具是“走一步看一步”——每用一个工具就要在推理轨迹里暴露一次调用、一次观察、一次值传递，就像厨师每切一次菜都要停下来写报告。这种执行粒度不匹配的问题在于，那些确定性的工具流程（比如排产规则中的换产时间计算）被拆成了无数个模型可见的决策步骤，既浪费上下文，又让模型去管理底层数据流。HyperTool的解法是把多个工具操作打包成一个代码块一次性执行，相当于给AI配了个“自动化流水线”，而不是让它每次拧螺丝都要请示。不过，这个方法的适用边界在于：它更适合那些流程确定、可预定义的子任务，对于需要动态探索或实时反馈的场景（比如突发异常处理），可能反而会丧失灵活性。

【一句话讲清楚它在说啥】
一个开源的桌面应用，让你用纯 Markdown 文件管理个人知识库，支持本地离线、Git 版本控制，并且原生对接 AI 工具来读写笔记。
【详细讲给你听】
背景是现在很多人用 Notion、Obsidian 这类笔记工具，但数据往往被锁在厂商的格式里，迁移麻烦，而且对 AI Agent 的支持不够原生。Tolaria 的创始人 Luca 自己管理着超过一万条笔记，他干脆造了一个轮子。核心思路是“文件优先”和“Git 优先”：你的笔记就是一堆纯 Markdown 文件，存在本地文件夹里，天然就是一个 Git 仓库。这意味着你可以用任何编辑器打开它们，用任何 Git 远程服务（如 GitHub）备份，完全不依赖 Tolaria 的服务器。关键细节有三点：第一，它内置了对 Claude Code、Codex CLI、Gemini CLI 等 AI 工具的配置路径，AI 可以直接读写你的整个知识库文件。第二，它用“类型”作为导航的“透镜”而不是强制 schema，比如你可以给笔记打上“项目”“想法”“日记”标签，但不会强制你填必填字段。第三，它完全离线可用，没有账号和订阅，你停止使用也不会丢失任何数据。影响上，这给知识管理领域提供了一个“反 Notion”的极简方案，特别适合那些想把个人知识库当成 AI Agent 上下文来用的开发者或重度用户。
【关键术语小词典】
无特殊术语。
【对你有啥用】
第一，这个“文件优先 + Git 优先”的架构思路，可以直接借鉴到你们决策智能平台的产品设计中。如果客户（比如电池厂）需要管理大量排产规则、工艺参数文档，用这种纯文件 + Git 版本管理的方式，比用数据库存文档更灵活，也更容易对接你们平台上的 AI Agent。第二，Tolaria 内置的 AI 配置路径（Claude Code、Codex CLI）是一个很好的产品设计参考。你们在做供应链优化产品时，可以考虑在平台里预设好主流 AI 工具的“接入模板”，让客户能一键把自己的知识库（如 SOP、排产规则）喂给 AI，降低使用门槛。第三，你个人做学习笔记或写产品文档时，可以试试用 Tolaria 替代 Obsidian，因为它对 AI 工具的支持更原生，能让你在 Cursor 或 Claude 里直接引用整个笔记库，提升内容产出效率。

【背景知识】
现在主流的笔记工具（Notion、Obsidian）虽然好用，但数据格式封闭、迁移成本高，而且对AI Agent的接入往往需要额外插件或API封装。Tolaria走的是另一个极端：纯Markdown文件 + Git版本控制，笔记就是本地文件夹里的.md文件，天然可被任何编辑器或AI CLI工具直接读写。这种设计牺牲了富文本和协作能力，但换来了极致的可迁移性和AI原生支持——你甚至可以让Claude Code直接遍历整个笔记目录作为上下文。

打破向量检索的局限：RAG 混合检索实践
InfoQ 中文 · 作者：Aaditya Chauhan · 昨天 10:49

【一句话讲清楚它在说啥】
这篇文章讲的是在 RAG（检索增强生成）系统里，光靠向量检索不够用，得把关键词搜索、结构化查询这些老办法混着用，才能让 AI 回答更准、更靠谱。
【详细讲给你听】
背景是现在很多 AI 应用都靠 RAG 来给大模型喂外部知识，但大部分实现只用了向量检索——就是把文本转成向量再算相似度。问题来了，向量检索对精确匹配、数字范围、日期筛选这些场景很弱。比如客户问“上个月电池 A 的订单金额”，向量检索可能把“电池 B”或“去年”的也拉出来，结果大模型回答就错了。这篇文章的核心是介绍“混合检索”的实践方案，就是同时跑向量检索、BM25 关键词检索、还有结构化过滤（比如 SQL 条件），然后把结果合并重排序。关键细节是：作者给出了一个具体的架构图，把检索拆成三条管道，最后用 RRF（倒数排序融合）算法打分合并。另一个值得注意的点是，文章强调混合检索不是简单拼凑，需要设计好权重和缓存策略，否则响应时间会翻倍。影响上，对咱们做企业级 AI 产品的来说，这意味着 RAG 系统的天花板被抬高了——之前客户抱怨“AI 瞎编”或“答非所问”，很多时候不是模型不行，是检索层太弱。混合检索就是补这块短板，让 AI 回答更贴近业务事实。
【关键术语小词典】
- RAG / 检索增强生成：让大模型先查资料再回答，减少胡说八道。
- BM25 / 一种关键词检索算法：根据词频和文档长度算相关性，传统搜索引擎的核心。
- RRF / 倒数排序融合：把多个检索结果按排名位置加权合并，简单有效。
- 向量检索 / 语义检索：把文本转成数字向量，找语义相似的片段。
【对你有啥用】
第一，直接对标你的工作场景。你们平台做供应链优化和排程算法，客户（电池、医药、钢铁）的查询往往涉及精确的订单号、批次号、日期范围。纯向量检索搞不定这些，混合检索是必须补的工程能力。第二，跟客户沟通时可以用这个点来“教育”市场。下次聊 RAG 落地，直接说“我们不光用向量，还混了关键词和结构化过滤，所以查排产计划比纯 AI 方案准 30%”，这能拉开跟竞品的差距。第三，对你个人学习路径有启发。你今年想深化 AI Agent 和 LLM 应用，混合检索是 Agent 工具调用和记忆管理的基础。建议你拿 Cursor 或 LangChain 跑一个混合检索 demo，把 BM25 和向量检索的权重调一调，感受一下召回率的变化。
