Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution

【一句话讲清楚它在说啥】
这篇论文发现当前 AI Agent 做任务时不管任务多简单都先读一遍所有文件，导致成本浪费。作者提出 E3 方法，让 Agent 先估算任务难度，只读必要文件，失败再扩展，结果在保证成功率的同时把成本降低了 85%。
【详细讲给你听】
背景是现在用大模型做 Agent 来写代码、改 bug 已经很常见，但你有没有发现一个问题：这些 Agent 不管任务多简单，都会先把整个代码库读一遍。比如你让它改一行代码，它可能先把整个项目文件都加载一遍，就像你让实习生去拿个快递，他先绕公司跑一圈再回来。核心问题是 Agent 缺乏“任务复杂度感知”能力，不知道这个任务到底需要多少信息。作者提出了一个叫 E3 的方法，分三步走：先估算任务需要的最小信息量，然后只读这些信息去执行，如果执行失败再扩展范围。他们在 MSE-Bench 这个基准上测试了 121 个代码编辑任务，结果特别惊人：E3 达到了和最强基线一样的 100% 成功率，但成本降低了 85%，token 使用量减少了 91%，检查的文件数减少了 92%。更厉害的是，他们在真实场景中用 GPT-4o 去改一个开源库，用真正的 pytest 测试来验证，结果 E3 是最快最省钱的方案，唯一的失败是 API 限速导致的，不是逻辑错误。这个工作提出了一个叫 ACRR 的指标来量化 Agent 的认知冗余，就是 Agent 做了多少不必要的思考。
【关键术语小词典】
ACRR / Agent Cognitive Redundancy Ratio：衡量 Agent 做了多少不必要工作的比例，越高说明越浪费。E3 / Estimate-Execute-Expand：三步法，先估算、再执行最小路径、失败再扩展。MSE-Bench：一个专门测试代码编辑任务的基准，包含 121 个确定性任务。
【对你有啥用】
第一，这对你做决策智能平台的产品设计直接相关。你做的排程算法本质上也是在“估算任务复杂度”——一个订单需要多少产能、多少物料，然后决定调度策略。这篇论文的思路完全可以搬到供应链优化里：让系统先估算订单的“执行复杂度”，只分配必要资源，不够再动态扩展，而不是每次都跑全量优化。第二，如果你在开发 AI Agent 产品，这个 E3 方法可以直接用在你的 Agent 架构里。比如你给客户做的智能排产助手，让它先判断客户问的是简单查询还是复杂优化，然后决定调用多少计算资源。第三，跟客户沟通时可以用这个案例。制造业客户最怕 AI 产品“大炮打蚊子”——明明改个参数就行，系统非要跑半小时。你可以说“我们参考了最新的复杂度感知方法，让系统先判断任务难度，简单任务秒级响应，复杂任务再深度计算”，这比讲技术细节更有说服力。

【背景知识】
当前主流 AI Agent 在接到任务时，缺乏对任务复杂度的预判能力，倾向于“先全量加载上下文再说”，导致大量 token 和计算资源浪费在无关文件上。这篇论文提出的 E3 方法本质上是一种“先估算、再执行、失败再扩展”的递归策略，类似你在排程算法里做“粗排+精排”的分层调度——先按最小资源试跑，不够再动态扩容，而不是上来就跑全量优化。不过要注意，E3 目前只在代码编辑场景验证，对需要全局上下文才能做判断的复杂任务（比如跨模块重构）可能不适用，而且估算环节本身也有额外的推理开销。
