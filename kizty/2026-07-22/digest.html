Keeping the Cache Warm Pays: Keepalive Economics for Agentic Workloads

【一句话讲清楚它在说啥】
这篇论文发现，AI Agent 在调用工具或等待审批的间隙，LLM 的缓存会被清掉，导致每次都要重新算一遍，成本高、速度慢。他们提出客户端定时发“心跳”请求来保持缓存，能把后续请求成本降低最多 12.5 倍。
【详细讲给你听】
背景是这样的：现在前沿的 LLM 提供商（比如 Anthropic、OpenAI）都会缓存你输入的前缀。如果你连续发两个差不多的请求，第二个请求只需要付 10% 的价格，而且跳过大部分预填充时间。但问题来了，Agent 工作流不是连续的——Agent 发一个请求，然后去调工具、等用户审批，可能几分钟后才发下一个。等它再发的时候，缓存已经被清掉了，Agent 得付全价重新算一遍。

这篇论文的核心发现是：在 Agent 空闲的间隙，客户端可以定时发一个“心跳”请求（keepalive），只重复发送前缀，让缓存保持活跃。他们测了 Anthropic、OpenAI、Google、DeepSeek 四家，发现这个策略能把暂停后的请求成本降低最多 12.5 倍。关键细节有三点：第一，最优的 ping 频率不是大家习惯的 30 秒，而是接近提供商 TTL（缓存存活时间）的最大安全间隔，比如 Anthropic 的 TTL 是 5 分钟，那就大约 4 分钟发一次。第二，这个策略的盈亏平衡点大约在 46 分钟（Anthropic）或 36 分钟（OpenAI/DeepSeek），也就是说，如果 Agent 空闲超过这个时间，keepalive 的成本反而比重新预填充高。第三，如果所有用户都用 keepalive，缓存会被占满，提供商基于 LRU（最近最少使用）的淘汰策略就失效了，论文认为这会倒逼提供商改为按缓存驻留时间计费。
【关键术语小词典】
- Keepalive / 心跳保持：客户端定时发请求，防止服务器或缓存超时断开。
- TTL / 存活时间：缓存数据在服务器上保留的有效时长，超时后会被清除。
- LRU / 最近最少使用：一种缓存淘汰策略，优先删除最久没被访问的数据。
- Prefill / 预填充：LLM 处理输入前缀的初始计算阶段，耗时且消耗算力。
【对你有啥用】
第一，你做的决策智能平台如果涉及 Agent 调用 LLM（比如排产建议的对话式交互），这个 keepalive 策略可以直接优化成本。下次跟客户聊时，可以提“我们通过缓存心跳机制，把 Agent 的推理成本降低了 10 倍”，这是很硬的卖点。第二，你关注 AI Agent 应用落地，这篇论文给了你一个产品层面的判断：Agent 的“空闲间隙”是设计上的隐藏成本点。你在设计供应链优化 Agent 时，要考虑工具调用和人工审批的等待时间，把 keepalive 做成默认配置，而不是让开发者自己调。第三，这篇论文的“经济学”视角对你做 PM 很有启发——它把缓存策略变成了一个可计算的成本模型，你可以在产品文档或客户沟通中引用这种“量化 ROI”的思路，比如“我们的 Agent 每 4 分钟发一次心跳，比行业默认的 30 秒节省 87% 的 keepalive 成本”。
