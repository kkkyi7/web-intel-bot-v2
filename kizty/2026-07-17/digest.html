【一句话讲清楚它在说啥】
中国 AI 实验室月之暗面发布了 2.8 万亿参数的 Kimi K3 模型，性能超越 GPT-5.5 和 Claude Opus 4.8，但定价也大幅上涨。作者还反思了自创的“鹈鹕骑自行车”测试已不再能有效衡量模型能力。
【详细讲给你听】
背景：中国 AI 实验室月之暗面（Moonshot AI）今天发布了其最强模型 Kimi K3，参数规模达到 2.8 万亿，号称首个“开放 3T 级模型”。它已通过官网和 API 提供服务，并承诺在 7 月 27 日开源权重。定价方面，输入每百万 token 3 美元，输出 15 美元，与 Anthropic 的 Claude Sonnet 系列持平，是中国 AI 实验室目前最贵的模型，相比前代 K2.6 的 0.95/4 美元大幅上涨。
核心：在自报的基准测试中，K3 大部分击败了 Claude Opus 4.8 max 和 GPT-5.5 high，但输给了 Claude Fable 5 和 GPT-5.6 Sol。在 Artificial Analysis 的评估中，K3 在长期知识工作评估中 Elo 得分 1547，比 K2.6 高 732 分，仅次于 Claude Fable 5。每任务成本 0.94 美元，接近 GPT-5.6 Sol 的 1.04 美元，约为 Opus 4.8 的一半。值得注意的是，K3 在 Arena.ai 的前端代码竞技场上超越了 Claude Fable 5，成为榜首。
关键细节：作者 Simon Willison 用自己 21 个月前发明的“鹈鹕骑自行车”测试（让模型生成 SVG 图片）来检验 K3。K3 生成了一个鹈鹕骑自行车的 SVG，消耗 95 个输入 token 和 16658 个输出 token（其中 13241 个是推理 token），总成本 25 美分。但作者指出，这个测试已经失效——它曾经与模型真实能力有惊人相关性，但现在 GPT-5.6 和 Claude Fable 5 的鹈鹕表现反而不如 GLM-5.2，而 GLM-5.2 远非 Fable 级别。最大的问题是，这个测试完全不涉及当前模型最重要的能力：智能体工具调用和在长对话中可靠操作工具的能力。
【关键术语小词典】
- Kimi K3 / 月之暗面 K3：中国 AI 实验室月之暗面发布的最新大语言模型，参数规模 2.8 万亿。
- Pelican benchmark / 鹈鹕基准测试：Simon Willison 自创的测试，让模型生成鹈鹕骑自行车的 SVG 图片，曾用于非正式评估模型能力。
- Elo 评分 / Elo 评分：一种用于衡量模型在对比测试中相对能力的评分系统，分数越高代表能力越强。
- OpenRouter / OpenRouter：一个聚合多家 AI 模型 API 的平台，用户无需单独注册各厂商账号即可调用不同模型。
【对你有啥用】
1. 产品判断：K3 定价策略值得关注——它主动对标 Claude Sonnet 而非最便宜的模型，说明月之暗面在走“高性能+高定价”路线。这对你做决策智能平台定价有参考：当你的排程算法或供应链优化模型性能显著提升时，是否应该同步提价？客户对“性能溢价”的接受度如何？
2. 客户沟通：K3 在“前端代码”领域超越 Claude Fable 5 是个具体卖点。下次跟制造业客户聊 AI 应用时，可以拿这个例子说明“特定场景下，国产模型可能比国际顶尖模型更优”。尤其当客户担心国产模型能力不足时，这个数据能直接打消顾虑。
3. 学习路径：作者对“鹈鹕测试”失效的反思很有价值——任何单一基准测试都会过时。你在评估 AI Agent 或 LLM 应用时，不要只看公开排行榜，要自己设计针对“智能体工具调用”和“长对话可靠性”的测试用例。这比盲目追 benchmark 更能指导产品落地。

Kimi K3 是月之暗面（Moonshot AI）最新发布的 2.8 万亿参数稀疏 MoE 模型，号称首个“开放 3T 级模型”，定价大幅上涨至输入 3 美元/百万 token、输出 15 美元，与 Anthropic Claude Sonnet 系列持平，是中国 AI 实验室目前最贵的模型。作者 Simon Willison 自创的“鹈鹕骑自行车”测试（让模型生成 SVG 图片）曾与模型真实能力高度相关，但现在已失效——因为当前最强模型的鹈鹕表现反而不如一些中低端模型，且该测试完全不涉及智能体工具调用和长对话中可靠操作工具的能力，这提醒我们：任何单一基准测试都有其边界，尤其是当模型能力重心转向 Agent 和工具使用时。

社区讨论集中在两点：一是 K3 的定价策略是否合理——虽然性能大幅提升，但成本已接近 GPT-5.6 Sol，对于工业软件 PM 来说，这意味着在客户沟通中需要更精细地评估 ROI，尤其是制造业客户对成本敏感；二是“鹈鹕测试”失效的启示——不少开发者认为，这类创意生成测试已无法反映模型在真实工作流（如 API 调用、多步推理）中的表现，建议关注更贴近实际场景的评测。

【详细讲给你听】
背景：现在 AI Agent 很火，但很多开发者或产品经理想快速验证一个想法时，往往要从头搭框架、调 API、写 prompt，效率很低。这个项目就是解决“从零到一”的痛点。核心：作者 Shubhamsaboo 把 100 多个自己亲手构建并测试过的 AI Agent 应用开源了。每个都是一个完整的、可运行的模板，你只要 git clone 下来，装个依赖，填个 API Key 就能跑。关键细节：1）支持 Claude、Gemini、GPT、DeepSeek、Llama、Qwen 等主流模型，不绑定单一厂商。2）项目分三层：Starter AI Agents（单文件，适合新手快速上手）、Advanced AI Agents（带工具、记忆和多步推理，适合生产级场景）、Agent Skills（可像插件一样安装到 Cursor、Claude Code 等编码 Agent 里，一条命令就能给编码 Agent 加新能力）。3）有个叫“Project Graveyard”的 Agent 技能挺有意思，它会扫描你废弃的 side project，分析为什么没做完，并建议哪个值得重启。影响：对开发者来说，这是一个“AI Agent 的乐高积木盒”，可以极大降低原型验证成本。对产品经理来说，这是一个绝佳的“竞品灵感库”和“客户演示素材库”。
【关键术语小词典】
- RAG / 检索增强生成：让大模型在回答前先去外部数据库查资料，减少胡说八道。
- Agent Skills / 智能体技能：可独立安装的 AI 功能模块，像给编码助手装插件。
- Apache-2.0 / 开源协议：允许自由使用、修改、商用，只需保留版权声明。
【对你有啥用】
1. 下次跟制造业客户聊“供应链决策智能”时，可以直接从这里面挑一个“AI Data Analysis Agent”或“AI Consultant Agent”做现场 demo，让客户看到“上传一个 Excel 排产表，用自然语言问问题就能出分析”，比 PPT 讲排程算法直观十倍。
2. 你今年想深化“工业软件+AI”的产品理解，可以把这些 Agent 模板当成“最小可行产品”的参考。比如“AI Home Renovation Agent”的思路，能不能改成一个“AI 产线排程 Agent”？用户拍一张车间布局图，Agent 自动生成排程方案和 3D 渲染图。

【关键术语小词典】
- dd-cli：DoorDash 的命令行工具，让用户或 AI 代理在终端里点外卖。
- CLI / Command Line Interface：命令行界面，用户通过输入文本指令操作电脑，不用鼠标点图标。
- AI Agent：AI 代理，能自主执行任务的程序，比如帮你下单、查天气。
【对你有啥用】
第一，这个思路可以直接用到你的决策智能平台里。你们做供应链优化和排程算法，如果给客户提供一个 CLI 工具，让他们的 AI 代理或自动化脚本直接调用排产、调度的接口，而不是每次都打开 UI 点来点去，能极大提升集成效率。第二，跟客户聊的时候可以提这个案例：连外卖平台都在做“AI 代理友好”的接口，说明工业软件也应该往这个方向走。你可以建议客户把他们的 APS 或 MES 系统也开放 CLI 或 API，让 AI 代理能直接接入。第三，对你个人学习 AI Agent 和开发者工具有启发：你可以自己试试写一个简单的 CLI 工具，调用某个公开 API（比如天气、股票），体验一下“为 AI 代理设计接口”和“为人设计接口”的差别，这对你理解产品形态转型很有帮助。

LangChain 发了小版本更新，核心是给工具调用加了两个中间件：一个专门处理可重试的错误，另一个统一拦截工具执行中的异常，让 Agent 更稳定。
【详细讲给你听】
背景是 LangChain 作为最流行的 AI Agent 框架，工具调用（Tool Calling）是核心能力。但之前工具执行出错时，重试逻辑比较粗糙，经常把不该重试的错误也重试了，或者异常信息直接抛出来打断流程。这次 1.3.14 做了两件事：第一，`ToolRetryMiddleware` 现在只对“可重试的异常”（比如网络超时、API 限流）进行重试，像参数错误这种重试也没用的就直接跳过，省时间省 Token。第二，新增了 `ToolErrorMiddleware`，相当于一个全局的“工具异常捕获器”，不管工具里报什么错，都能统一拦截、格式化，然后返回给 LLM 一个友好的错误消息，而不是让 Agent 直接崩溃。这两个中间件都是通过 LangChain 的 `Runnable` 链式调用来集成的，配置起来就几行代码。对开发者来说，这意味着写 Agent 应用时不用自己写一堆 try-catch 和重试逻辑了，框架帮你兜底。
【关键术语小词典】
- ToolRetryMiddleware / 工具重试中间件：只对网络波动等可恢复错误自动重试，避免无效重试浪费 Token。
- ToolErrorMiddleware / 工具错误中间件：统一捕获工具异常，返回结构化错误信息给 LLM，防止 Agent 崩溃。
