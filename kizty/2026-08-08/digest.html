工具调用的苦涩教训
The Bitter Lesson of Tool Calling
arXiv · Ishan Patel, Sahil Sen, Elias Lumer, Vamse Kumar Subbiah · 2 天前
⌄
http://arxiv.org/abs/2608.06370v1
【相关性评分】
9
【一句话讲清楚它在说啥】
这篇论文对比了让大模型用写代码的方式调用工具，和传统用 JSON 格式调用工具的效果。结果发现写代码的方式在大多数模型上表现更好，尤其对 GPT-5.6 提升明显，而且更稳定。
【详细讲给你听】
背景是这样的，现在大模型要调用外部工具，比如查天气、算数据，标准做法是让模型输出一个 JSON 格式的指令，然后系统去执行。但 JSON 格式有局限，复杂任务要写很长，而且不好并行。这篇论文提出一个更自然的思路，既然模型会写代码，那就直接让模型写 Python 代码来调用工具，代码里天然支持循环、条件、并行这些逻辑。

核心实验是在 BFCL v4 这个标准评测集上，对比了 14 个主流模型。结果发现，用代码调用工具的方式在 11 个模型上不输给 JSON 方式，其中 GPT-5.6 家族提升了 10.6%。在需要并行处理多个工具调用时，14 个模型里有 13 个表现更好或持平。还有个有意思的发现，在上下文被干扰的情况下，JSON 方式平均下降 2.3%，但代码方式基本不受影响。

机制上其实不难理解，代码本身就是一种为表达复杂逻辑设计的语言，让模型用代码表达意图，比用扁平的 JSON 结构更符合它训练时的数据分布。而且代码可以一次执行多个操作，不用来回多轮对话。这篇论文的价值在于，它用系统性的实验证明了这条路是通的，而且越强的模型收益越明显。
【关键术语小词典】
PTC / Programmatic Tool Calling：程序化工具调用，让模型写代码来调用外部功能
JSON Tool Calling：用 JSON 格式描述工具调用请求的传统方式
BFCL v4：伯克利函数调用评测集第四版，专门测模型调用工具的能力
GPT-5.6：OpenAI 的新一代模型系列，本文测试中表现最强的模型
【对你有啥用】
第一，你做的决策智能平台如果涉及让大模型调用排程算法或供应链优化模块，现在可以认真考虑用代码调用替代 JSON 调用。跟客户演示时，这个结论可以直接支撑你的技术选型，说这是有论文数据背书的。第二，这个思路对你理解 Agent 架构演进很有帮助，代码即接口这个方向可能会成为 Agent 开发的主流范式，你跟进学习 AI Agent 时可以重点看这个方向。第三，你关注开发者工具方向，这个结论意味着未来 Agent 开发框架可能会更强调代码生成能力，而不是配置化界面，这对你判断工具产品的设计取向有参考价值。

【背景知识】
传统上，大模型调用外部工具（比如查天气、执行计算）的标准做法是让模型输出一个符合 JSON Schema 的指令，然后由外部系统解析并执行。这种方式虽然简单，但表达复杂逻辑（比如循环、条件分支、并行调用）时很笨拙，而且每调用一次工具就要多一轮模型推理，延迟和成本都上去了。这篇论文提出的思路是：既然模型已经会写代码，不如直接让它生成 Python 代码来调用工具，代码本身就能天然表达复杂逻辑，还能一次执行多个操作。不过要注意，这个结论是在 BFCL v4 这个特定评测集上得出的，实际生产环境里代码调用的安全性、可调试性、对模型代码能力的依赖，都是需要权衡的坑。
【社区讨论】
社区讨论集中在两点：一是代码调用是否真的能成为 Agent 工具调用的主流范式，有开发者认为这会让 Agent 的调试和可观测性变得更难，因为代码执行出错时定位问题比 JSON 更麻烦；二是对 GPT-5.6 提升幅度（71.9%→96.9%）的质疑，有人指出这可能是因为该模型在训练时对代码生成做了特别优化，不代表所有模型都能吃到同样的红利。

【一句话讲清楚它在说啥】
这个开源项目能把多个 Grok 账号池化，统一成 OpenAI 和 Anthropic 兼容的 API 接口，方便开发者用官方渠道没有的方式批量调用 Grok 模型。
【详细讲给你听】
背景是 Grok 官方 API 的获取门槛和成本对很多开发者不友好，而 Grok 的网页版和 Console 版其实有可用额度。这个项目就钻了这个空子，把多个 Grok 账号集中管理，通过一个网关统一暴露成标准 API。核心是它用 Go 写了个网关，带 React 管理后台，能分别管理 Grok Build、Web、Console 三种账号池，然后输出成 OpenAI 和 Anthropic 兼容的接口格式。关键细节有三个：一是支持 OAuth 和 SSO 登录方式，能动态同步账号的配额和模型列表；二是内置了路由、重试和审计功能，相当于一个小型 API 管理平台；三是项目声明仅供技术研究，要求遵守 Grok 使用条款。影响方面，这类项目降低了调用前沿模型的门槛，但也游走在官方条款的灰色地带。对做产品的你来说，它展示了一种多账号资源池化的架构思路，这在企业级 AI 平台里其实是个常见需求。
【关键术语小词典】
API 网关：统一接收请求并转发到后端服务的入口，负责路由、鉴权、限流。
OAuth：一种授权协议，允许第三方应用安全地访问用户资源，不用暴露密码。
SSO：单点登录，一次登录就能访问多个关联系统。
配额：账号可使用的资源上限，比如调用次数或 Token 数。
【对你有啥用】
第一，你做的决策智能平台如果未来要接入 Grok 或其他模型，这种多账号池化网关的架构设计可以直接参考，特别是账号配额同步和动态模型列表这块，跟企业客户的多租户管理场景很像。第二，下次跟客户聊 AI 落地时，可以提一句开源社区已经有成熟方案解决模型接入的账号管理和成本优化问题，这能体现你对生态的敏感度。第三，这个项目的设计模式，也就是把非标准接口统一成 OpenAI 兼容格式，正是你所在平台的核心价值之一，值得拆解它的实现细节。

【详细讲给你听】
背景是 Postgres 在事务处理上很强，但分析型查询一直被人诟病慢，很多团队被迫引入 ClickHouse、DuckDB 这类列存引擎来处理报表场景，导致架构里多一套系统要维护。这个叫 pgrust 的项目思路很直接，不动 Postgres 的存储和协议，只把查询执行引擎用 Rust 重写，核心用了三招。第一是批处理，不再一行一行处理数据，而是一批一批来，减少函数调用和上下文切换的开销。第二是算子融合，把过滤、投影、聚合这些操作合并成一次循环，避免中间结果反复物化。第三是 SIMD，让 CPU 一次处理多条数据，充分利用现代处理器的向量指令。作者说过去两周做了形式化验证和差分模糊测试，证明超过一千个用户可见函数在 pgrust 和原版 Postgres 里逻辑完全一致。HN 讨论里有人质疑生态信任问题，觉得大家不会为了快就换掉官方团队维护的东西，也有人期待自适应执行计划能倒逼官方跟进。这项目目前还在早期，但方向很明确，就是让 Postgres 在分析场景下不用换数据库也能打。
【关键术语小词典】
pgrust：用 Rust 重写 Postgres 查询引擎的开源项目，目标是提升分析查询性能。
算子融合：把多个数据处理步骤合并成一次遍历，减少中间结果生成和内存拷贝。
SIMD：单指令多数据，让 CPU 一条指令同时处理多条数据，是性能优化的常用手段。

Entropy-aware filtering and hierarchical attention: A hybrid neural framework for fine-grained user satisfaction modeling.

【相关性评分】

【一句话讲清楚它在说啥】
这篇论文提出一个混合神经网络框架，用熵机制过滤无效评论，再用层级注意力做情感分析，最后结合模糊决策算用户满意度，在出行服务评论上比12个基线模型准1.4%到5.6%。
【详细讲给你听】
背景是这样的。现在网上用户评论爆炸式增长，但评论质量参差不齐，很多是废话、水军或者情绪发泄。传统方法要么靠点赞数判断评论有没有用，要么直接拿所有评论做情感分析，噪音太大，结果不准。这篇论文想解决的就是这个事。

核心是他们搞了一个三件套的框架。第一件是熵机制，用来预测一条评论的信息量，说白了就是先筛一遍，把没营养的评论扔掉。第二件是层级特征提取，用PERT增强的BERT编码器，把评论从词到句到整篇一层层抽特征。第三件是情感值预测，用BERT-wwm-ext加层级注意力门控网络，把情感倾向算出来。最后再用模糊决策的加权和排序策略，把多维度的满意度汇总成一个数。

关键细节有三个。一是他们在出行服务系统的18559条真实评论上做了实验，数据量不算大但很真实。二是比12个基线模型提升了1.4%到5.6%，这个幅度在NLP任务里算不错了。三是他们特别强调解决了传统投票机制的问题，就是点赞数高不代表信息量大，这条对产品经理特别有共鸣。

机制上可以这么理解。传统方法像是一个餐厅经理只看大众点评的星级和评论条数，但这篇论文的做法是，先让一个助理把刷屏的、复读机的评论扔掉，再让几个分析员从不同角度读剩下的评论，最后加权汇总成一份报告。这套流程本质上就是"数据清洗加多维度评估"，跟咱们做用户调研的思路一模一样。
【关键术语小词典】
熵机制：衡量信息混乱程度的数学工具，这里用来判断评论有没有信息量。
PERT：一种BERT的轻量变体，训练效率更高，适合做特征提取。
BERT-wwm-ext：全词掩码的中文BERT增强版，对中文文本理解更细。
模糊决策：用隶属度处理不确定性的决策方法，适合多指标加权打分。
【对你有啥用】
第一，这套"先过滤噪音再分层建模"的思路可以直接搬到你做的排程算法里。工业现场的数据跟用户评论一样，大量是冗余的报警、日志、传感器噪音，你完全可以在预处理阶段加一个熵机制，先筛掉无效信号再跑优化，效果可能比直接调参更明显。

第二，下次跟客户聊"满意度"的时候可以提这个框架。制造业客户经常说"我们想量化客户满意度"，但拿出来的数据就是投诉率和退货率。你可以用这篇论文的多维度加权思路，帮他们设计一个更细的满意度指标体系，比如交付准时、质量稳定、响应速度各占多少权重，这比单一指标有说服力得多。

第三，对你学习AI Agent有启发。这个框架里的"层级注意力"本质上就是让模型先看局部再看全局，跟Agent里"先规划再执行"的层级结构是相通的。你在设计Agent工作流时，也可以考虑加一个"信息过滤层"，让Agent先判断哪些输入值得处理，而不是所有请求都走完整流程，能省不少token。
