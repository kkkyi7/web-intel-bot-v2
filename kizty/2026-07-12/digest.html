【详细讲给你听】
背景是 OpenAI 和 Anthropic 的模型竞赛进入白热化，这次 GPT-5.6 系列直接对标 Claude Fable 5。核心是三个模型按大小定价：Luna 最便宜（$1/$6 每百万 token），Terra 中等（$2.50/$15），Sol 最贵（$5/$30）。关键细节一：在 Agents’ Last Exam 这个覆盖 55 个领域的专业工作流测试中，Sol 以 53.6 分碾压 Fable 5 的 40.5 分，即使在中档推理模式下也领先 11.4 分，成本只有四分之一。关键细节二：但 SWE-Bench Pro 编程测试中，Fable 5 拿到 80%，Sol 只有 64.6%，OpenAI 还提前发文质疑该基准有 30% 的任务有问题。关键细节三：API 新增了程序化工具调用（模型自己写 JavaScript 编排工具调用）、多智能体（模型自动创建子代理并行工作）、提示缓存断点等功能。作者 Simon Willison 提前体验后说，Sol 在复杂编程任务上还没觉得比 Fable 强。这本质上是一场“长任务能力 vs 编程能力”的差异化竞争，对开发者来说，选择模型不再只看价格，还要看场景。
【关键术语小词典】
- Agents’ Last Exam / 代理最终考试：评估模型在 55 个专业领域执行长工作流能力的基准测试。
- SWE-Bench Pro / 软件工程基准专业版：专门测试模型解决真实 GitHub 代码问题的基准。
- Programmatic Tool Calling / 程序化工具调用：模型能自己写 JavaScript 代码来编排多个工具调用，类似让模型当“脚本调度员”。
- Multi-agent / 多智能体：模型在 API 层面支持自动创建子代理并行处理任务，不用开发者自己写调度逻辑。
【对你有啥用】
三条直接启发。第一，你做的决策智能平台如果涉及排程算法，可以关注“多智能体”模式——模型自动拆分子任务并行计算，这跟你做供应链优化里的并行排产思路很像，下次跟客户聊“AI 如何自动协调多产线”时可以直接引用这个技术点。第二，SWE-Bench 的争议对你做产品判断很有价值：OpenAI 质疑基准本身有问题，说明在工业软件领域，你给客户做 POC 时一定要自己设计测试场景，别盲目信第三方基准，尤其是电池、医药这些行业有自己独特的排产逻辑。第三，程序化工具调用这个能力，意味着未来 AI 可以自动调用你平台里的排程 API、BOM 查询、库存接口，你作为 PM 应该思考怎么把产品接口设计成“可被 AI 程序化调用”的格式，这可能是你产品差异化的关键。

Google 给 Gemini API 的托管智能体加了三个新功能：支持后台长时间运行任务、能连远程 MCP 服务器、还有更好的错误处理，让开发者能做出更靠谱的 AI 应用。
【详细讲给你听】
背景是之前用 Gemini 做智能体，任务一跑就卡住，或者只能处理简单对话，没法做像“自动监控供应链库存并生成补货建议”这种需要跑很久的活儿。这次更新核心是三个点：第一，后台任务功能让智能体可以跑几小时甚至几天，比如半夜自动跑一遍排产方案，早上给你结果。第二，远程 MCP 支持，意味着智能体可以调用外部工具和数据源，比如直接连上你公司的 APS 系统或数据库，不用把数据搬来搬去。第三，新增了“确定性执行”模式，就是给智能体加了个“检查清单”，确保每一步都按规矩来，不会乱跳步骤。关键细节是 Google 说这些功能已经在内部测试中让开发效率提升了 40%，而且错误率降低了 60%。影响是这直接让 AI 智能体从“玩具”变成了“生产工具”，尤其适合工业软件里那些需要跟多个系统交互、跑长流程的场景。
【关键术语小词典】
- Managed Agents / 托管智能体：Google 帮你维护服务器和运行环境的 AI 程序，你只管写逻辑。
- MCP / 模型上下文协议：一种让 AI 模型安全调用外部工具和数据的标准接口。
- 确定性执行 / Deterministic Execution：让 AI 每一步都按预设规则走，不随机发挥，保证结果可重复。
【对你有啥用】
第一，这个后台任务功能直接对应你做的排程算法场景。以前客户说“我要跑一个小时的优化方案”，你可能得搞个异步队列，现在 Gemini 原生支持了，下次跟客户聊技术方案时可以提“Google 已经把这个做成标准功能了”，显得你跟进前沿。第二，远程 MCP 支持意味着你可以让智能体直接连客户的 MES 或 ERP 系统，不用再纠结数据导出导入的安全问题，这对你推决策智能平台进制造业工厂是个很好的卖点。第三，确定性执行模式对工业客户特别重要，他们最怕 AI 乱来，这个功能能让你在演示时强调“每一步都可审计可回放”，降低客户的信任门槛。

MCP（模型上下文协议）是 Anthropic 去年推的一个开放标准，本质是给 AI 模型一个统一的“插头”，让它们能安全地调用数据库、API 或本地文件，避免每家厂商自己搞一套私有协议。Google 这次在 Gemini API 里原生支持远程 MCP，等于承认了这个方向，也意味着你不需要再为每个客户定制智能体对接方式——只要对方系统支持 MCP，就能直接连。不过要注意，MCP 目前生态还在早期，很多工业软件（比如老牌 MES/ERP）不一定原生支持，实际落地时可能还得写适配层。

SQLite 的严格模式能强制字段类型，防止数据污染，但默认不开启。社区讨论是否该改默认，以及如何把旧表转成严格表。
【详细讲给你听】
背景是 SQLite 默认的“柔性类型”允许你把文本塞进整数字段，这在传统企业数据库里是灾难，但 SQLite 设计者认为这种错误容易发现和修复，所以不打算改默认。核心是这篇博客和 HN 讨论在争论：到底该不该用严格模式。关键细节有三点：第一，有个叫 simonw 的开发者给 sqlite-utils 工具加了功能，一行命令就能把非严格表转成严格表，比如 `uvx sqlite-utils transform data.db mytable --strict`。第二，SQLite 官方文档解释为什么严格模式不是默认——他们认为类型错误很容易定位，没必要牺牲灵活性。第三，有评论者反对严格模式，因为它限制了应用层用更丰富的类型名（比如用 Rust 的 sqlx 时），反而让代码更难维护。影响上，如果你是做工业软件或供应链系统，数据一致性比灵活性重要得多，严格模式能避免排产数据里混入垃圾值，直接减少调试时间。
【关键术语小词典】
- STRICT tables / 严格表：强制每列数据类型，插入错误类型会报错，类似传统 SQL 数据库。
- sqlite-utils：一个 Python 库和命令行工具，方便操作 SQLite 数据库，作者是 simonw。
- flexible typing / 柔性类型：SQLite 默认行为，允许任意类型数据存入任意列，不报错。
【对你有啥用】
第一，你做的决策智能平台涉及电池、医药等制造业，客户数据质量要求极高。在 SQLite 原型或嵌入式场景里，强制用严格表能避免因类型错误导致排程算法读入脏数据，减少客户现场排查成本。第二，下次跟客户聊数据治理时，可以提“我们底层用严格模式保证字段一致性”，这比解释柔性类型更符合制造业客户的预期。第三，如果你在探索用 SQLite 做轻量级 AI Agent 的本地存储（比如缓存 LLM 调用结果），严格表能防止意外写入错误类型，让 Agent 行为更可预测。

背景是 Transformers 是 AI 领域最常用的模型加载和运行库，而 vLLM 是现在工业界非常流行的 LLM 推理加速引擎，很多企业用 vLLM 来部署大模型做推理服务。这次补丁的核心就是让 Transformers 能兼容最新版的 vLLM。具体修复了三个问题：一是对自定义模型的旧层类型做了更安全的映射，防止加载时报错；二是修复了自定义代码不认识新线性层类型名的问题；三是修复了懒加载映射时传入字符串键导致的问题。说白了，就是当你在 vLLM 里加载一个用 Transformers 保存的模型时，如果模型用了自定义结构，之前可能会崩，现在更稳了。这对做 AI 应用落地的团队是个好消息，意味着推理部署的兼容性更好，少踩坑。
【关键术语小词典】
- Transformers / HuggingFace Transformers：最流行的开源深度学习模型库，支持加载和运行 GPT、BERT 等模型。
- vLLM / 高性能推理引擎：专门加速大模型推理的开源框架，能显著提升吞吐量，降低显存占用。
- Patch release / 补丁版本：修复 bug 或做小改进的版本，不引入新功能。
【对你有啥用】
第一，你关注 AI Agent 和 LLM 应用落地，这个补丁说明 vLLM 和 Transformers 的生态整合在加速。如果你团队在部署模型做决策智能应用，用 vLLM 做推理后端会更稳定，少处理兼容性报错。第二，对产品经理来说，理解底层工具的版本依赖关系很重要。跟客户聊 AI 落地时，可以提“我们用的推理引擎是工业级方案，持续跟进最新版本”，增加技术信任感。第三，这个补丁的修复思路值得学习：做产品时，对“自定义”和“边缘情况”要更防御性处理，很多线上事故都来自没覆盖到的特殊配置。
