Superpowers：编码智能体的技能框架与开发方法论
obra/superpowers

【一句话讲清楚它在说啥】
这是一个给 AI 编码智能体用的完整开发方法论框架，让智能体从写代码前先问清需求、出设计文档、按 TDD 节奏执行，还能自主跑两小时不跑偏。
【详细讲给你听】
背景是现在用 Claude Code、Cursor 这类编码智能体的人越来越多，但大家普遍遇到一个问题：智能体一上来就闷头写代码，写出来的东西跟需求对不上，改来改去效率很低。这个项目叫 Superpowers，作者是 GitHub 上一个挺有名的开发者 obra，他做了一个插件框架，核心思路是给智能体装上一套"工作流程"和"技能包"。它怎么工作呢，智能体启动后不会直接动手写代码，而是先停下来问你到底要解决什么问题，把需求聊清楚之后，它会分块给你看规格说明，让你能真正读进去、确认没问题。然后它再出一个实施方案，这个方案详细到什么程度呢，作者说"清晰到让一个没品味、没判断力、没项目背景、还讨厌写测试的初级工程师都能照着执行"。方案里强调真正的红绿 TDD、YAGNI 和 DRY 原则。你点头说"开始"，它就启动一个子智能体驱动的开发流程，每个工程任务都由子智能体去完成，然后检查、审查、继续推进。作者说智能体自主工作两小时不偏离计划是常有的事。关键细节是这套技能是自动触发的，你不需要手动去调什么，装上插件，你的编码智能体就自动有了这套能力。它支持 Claude Code、Cursor、Codex、Gemini CLI、Copilot CLI 等几乎所有主流编码智能体工具。这个项目的意义在于，它把"怎么让 AI 写好代码"从提示词技巧提升到了方法论层面，等于给智能体装了一套软件开发流程的"操作系统"。
【关键术语小词典】
TDD：测试驱动开发，先写测试再写代码，确保每个功能都有验证。
YAGNI：你不需要它，不要提前做用不上的功能。
DRY：不要重复自己，相同逻辑只写一份。
Claude Code：Anthropic 出的命令行编码智能体工具。
【对你有啥用】
第一，你平时做产品肯定要跟研发协作，这个框架的核心思路"先对齐需求再动手"跟产品经理的工作方式完全一致，你可以把它当作跟研发团队沟通的参考案例，尤其是"规格说明分块展示"这个做法，直接可以借鉴到你写 PRD 和需求评审的节奏里。第二，你关注 AI Agent 落地，这个项目是 agentic 方法论的一个标杆案例，它展示了怎么把隐性经验显性化成可复用的技能包，这个思路对你设计决策智能平台里的"工作流模板"或"最佳实践库"很有参考价值，比如供应链排产场景里能不能把老师傅的排产经验也做成类似的技能包。第三，你今年想深化 AI 应用理解，建议直接装上这个插件在 Claude Code 里跑一个真实的小项目，体验一下"智能体先问需求再写代码"的完整流程，这个体感比读十篇文章都管用。

AI4AI-Bench：评测LLM智能体递归自我改进的算法设计能力
AI4AI-Bench: Benchmarking LLM Agents in Algorithmic Design for Recursive Self-Improvement
arXiv · Yizhe Chi, Wenyi Li, Deyao Hong, Xiaoqiu Wang, Mingju Gao, Kaisen Yang, Bingxiang He, Youjie Zheng, Calvin Xiao, Qinhuai Na · 3 天前
⌄
http://arxiv.org/abs/2608.20318v1
【相关性评分】

【一句话讲清楚它在说啥】
这篇论文发布了一个叫AI4AI-Bench的基准测试，专门检验AI智能体能不能自己改进训练算法。结果发现，目前最强的系统也只能完成不到五分之一的最优改进，说明AI自我改进这条路还非常早期。
【详细讲给你听】
这篇论文解决的是一个很根本的问题：AI能不能自己改进“制造AI的算法”？以前大家说的“递归自我改进”大多停留在概念层面，因为没人能单独测出“智能体改进训练算法”这个能力。现有的基准测试要么靠堆数据，要么靠调超参数，没法把“改执行方式”和“改学习方式”分开。

作者搞了10个冻结的研究代码库，覆盖10类训练算法家族。每个任务里，智能体有4小时在一张B300显卡上重写训练算法，然后代码从头再跑最多12小时，用隐藏的评估器打分。他们把10个任务的分数统一映射到0到1的尺度，0代表无信息模型，0.1是仓库原算法，1.0是任务最优。

结果挺扎心的：6个系统在29种配置下，平均分只有0.166，最好的也就0.250，连“仓库已有算法到最优”之间距离的五分之一都没走完。更关键的是，大多数提交根本没改变模型的学习方式，只有少数改了，这部分平均分0.226，比没改的0.126高不少。加大推理预算确实有用，能让“敢改学习方式”的提交从8%涨到64%，平均分从0.094提到0.196。

这个基准的厉害之处在于，它把“改算法”和“改数据/超参”彻底分开了，而且所有代码、评估器和提交都开源，方便后续重复测量。
【关键术语小词典】
RSI（递归自我改进）：AI系统改进“制造AI的过程”，让下一代系统继承改进。
AI4AI-Bench：本文发布的基准测试，专门测智能体设计训练算法的能力。
B300：英伟达的GPU型号，本文实验用的算力硬件。
训练算法家族：指不同类别的训练方法，比如损失函数设计、更新规则等。
【对你有啥用】
第一，这个基准的“隐藏评估器”设计思路可以直接借鉴。你做决策智能平台，客户总说“你的优化方案比我们现在的排产好”，但怎么证明？可以学他们：固定评估流程，把客户现有算法作为基线0.1，最优解作为1.0，用统一尺度量化改进幅度，跟客户沟通时更有说服力。

第二，论文结论“多数智能体不敢改学习方式，加大推理预算才敢”对你做AI Agent产品有直接启发。现在很多Agent产品只做“调用工具”，不敢动核心逻辑。这提示你，在给制造业客户设计Agent时，可以分层：先让Agent改参数、改配置，再逐步开放改规则、改流程的权限，降低客户信任门槛。

第三，这个基准的“任务映射到统一尺度”方法，对你做多客户、多场景的决策智能平台很有用。不同工厂的产线、物料、订单结构都不一样，指标不可比。你可以用类似思路，把每个客户的优化目标映射到统一尺度，做跨客户的效果对比，这对产品标准化和销售话术都是加分项。

【一句话讲清楚它在说啥】
OpenAI 在 GPT-5.6 更新后，让 ChatGPT 搜索大量自动使用 site: 语法来限定来源网站，Reddit 被引用的比例明显下降，这背后是生成式引擎优化（GEO）这个新赛道的兴起。
【详细讲给你听】
这事儿得从两个角度拆开看。第一是 OpenAI 的动作：Promptwatch 这家做 GEO 监控的公司，通过自动化追踪 ChatGPT、Claude、Gemini 等产品对用户提示词的回复，发现从 8 月 8 号 GPT-5.6 正式铺开之后，ChatGPT 搜索里带 site: 操作符的查询比例从之前的 0.3% 到 0.5% 直接跳到了 16% 到 17%，涨了大概四十倍。这基本坐实了 OpenAI 在系统层面主动引导搜索去限定域名来源，而不是靠模型自己瞎猜。第二是 Reddit 的失宠：8 月 18 号 Promptwatch 又报告说 ChatGPT 搜索里 Reddit 被引用的概率大幅降低。作者 Simon Willison 自己扒系统提示词没找到明确证据，但结合 OpenAI 8 月 6 号那句含糊的“更可靠的事实、更聚焦的答案”的公告，可以推断他们调整了搜索工具的底层逻辑，可能变成了类似 search(query, recency, domains) 这样的函数调用，直接让模型指定域名。这件事对做内容生态和搜索产品的人是个信号：AI 搜索正在从“开放抓取”走向“受控检索”，谁被算法选中谁就获得流量，这跟当年 SEO 的玩法完全不同了。
【关键术语小词典】
site: 操作符：搜索引擎语法，用来限定只在某个网站内搜索，比如 site:reddit.com 只搜 Reddit 的内容。
GEO：生成式引擎优化，就是让网站内容更容易被 AI 聊天机器人引用和推荐，相当于 AI 时代的 SEO。
Promptwatch：一家监控 AI 聊天产品回复变化的第三方工具公司，靠自动化追踪提示词响应来做数据分析。
GPT-5.6 Sol：OpenAI 在 2026 年 8 月发布的模型更新版本，主打事实可靠性和回答聚焦度。
【对你有啥用】
第一，你做的决策智能平台本质上是帮客户从数据里找答案，ChatGPT 搜索这个“限定域名”的思路可以直接借鉴到排产算法里：与其让模型在全部历史数据里乱找，不如先根据订单类型、产线属性限定数据源范围，再跑优化，效果和效率都会提升。第二，你跟制造业客户聊 AI 落地时，可以拿这个案例说明“AI 的输出质量取决于检索策略”，不是模型越大越好，而是怎么控制输入源，这对说服客户接受你的平台方法论很有帮助。第三，GEO 这个赛道对你们公司有直接意义：如果你们有对外输出的内容（比如行业白皮书、技术博客），现在就该研究怎么让 ChatGPT 在回答供应链问题时引用你们的内容，这比投广告划算得多。

【一句话讲清楚它在说啥】
开发者工具 llm 发布 0.33 版本，升级了底层库，给嵌入模型加了独立的 key 支持，还能把多个模板串起来用，方便组合模型和参数。
【详细讲给你听】
Simon Willison 维护的 llm 命令行工具发新版本了。这工具是给开发者用的，让你在终端里直接调用各种大模型，不用写一堆代码。这次 0.33 版有几个挺实在的更新。第一个是把底层的 OpenAI 库升到 3.x，HTTP 客户端也换了，属于常规技术升级，但能保证以后兼容性更好。第二个是对嵌入模型的支持更灵活了，以前调嵌入模型只能用全局的 API key，现在可以像普通模型一样，每次调用单独传 key，这对同时用多家模型服务的人来说很方便，不用来回切换配置。第三个是模板功能变强了，以前一个命令只能套一个模板，现在能重复使用 -t 参数把多个模板按顺序组合起来。举个例子，你可以先存一个"高推理强度"的模板，再存一个"画一只骑自行车的鹈鹕"的提示词模板，然后一条命令把两个模板串起来，就能用高推理强度的模型去生成这个 SVG。最后还加了个 reasoning_summary 参数，可以控制推理模型返回摘要的详细程度。整体看下来，这版本没有颠覆性功能，但每个改动都在解决实际使用中的痛点，属于那种"用了就回不去"的体验优化。
【关键术语小词典】
httpx2：一个 Python 的 HTTP 客户端库，新版 llm 用它替代了旧的 httpx。
EmbeddingModel：嵌入模型，把文本转成向量，用于语义搜索和相似度计算。
Responses API：OpenAI 的接口规范，支持推理模型返回思考过程摘要。
模板组合：把多个预设的模型配置和提示词拼接成一条完整命令。
【对你有啥用】
这个工具的思路可以直接映射到你的决策智能平台上。第一，模板组合这个设计，很像你平台里"场景配置"和"算法参数"解耦的思路，下次跟客户聊排程方案时，可以提"把行业经验沉淀成模板，现场灵活组合"这个概念，客户容易理解。第二，嵌入模型支持独立 key，说明多模型混合调用是刚需，你在设计平台的多模型管理功能时，要考虑每个模型实例独立鉴权，别做成全局共享。第三，Simon 这种小步快跑、每个版本解决几个具体痛点的迭代节奏，值得你参考，不用憋大招，把用户反馈的高频问题拆成小版本发布，反而能建立信任。
